# Academic Slide Forge

Use one project analysis, one page plan, and one primary renderer per deliverable. Derive content and visual decisions from the current project; keep case-specific facts in its workspace and load domain references only when relevant. This is an agent workflow with an image adapter, not a fully implemented presentation application. Never equate a valid skill file, a running preview server, or a successful image request with a visually accepted deck.

## Start or resume here

Use this skill as the presentation workflow; use renderer libraries directly rather than importing another complete presentation skill. If a mandatory active instruction conflicts with the selected renderer, identify that conflict once and resolve it under the instruction hierarchy; repeatedly rereading both guides cannot resolve it.

Before project discovery, run `python <skill-dir>/scripts/workflow_state.py status --workspace <deck-workspace>` and read the existing `research_checkpoint.md` when present. No state file means unknown progress, not a new project: inspect existing artifacts first. For an existing run, verify the recorded files and perform its concrete next action unless changed evidence, missing artifacts or the current user request requires a targeted correction. Do not reconstruct an existing plan just because context was compacted.

For a new project, read [research-continuity.md](references/research-continuity.md) and [visual-reasoning.md](references/visual-reasoning.md), then begin whole-project analysis. Read [execution-state.md](references/execution-state.md) once when initializing or repairing the execution ledger. Save findings in the checkpoint and record each meaningful batch/action with the helper. It reports changed/missing files and repeated batches without reported progress; it does not verify facts, drive an autonomous loop or approve quality.

Load references for the current stage only: analysis uses continuity/visual reasoning; planning uses page contract/project visuals/layout/renderer routing; sample production adds the selected image/export instructions and [mechanism-gates.md](references/mechanism-gates.md) for every mechanism or explanation page; final validation uses quality gates/QA/export instructions. Motion and domain references are conditional. During recovery, reload a relevant section if its rule is no longer available; do not recursively read every linked guide. Advance based on evidence sufficiency, never elapsed time or a quota of files read. Two recorded batches without a new finding or changed artifact require diagnosing the precise blocker before further discovery; necessary targeted research can continue.

## Working sequence

Honor an explicitly selected image backend for both design concepts and component assets. If the user chooses a dedicated image relay, read `references/proxy-backend.md` and use its configured runner; the chat provider's native image tool is a separate backend, not a substitute. Record the selection in the deck's asset plan/checkpoint and preserve it on resume. See `references/image-pipeline.md` for recovery from unsupported native image parameters.

When building a material library or improving weak generated imagery, read [visual-reference-library.md](references/visual-reference-library.md). Inspect actual domain figures and project assets, but distinguish research references from generation inputs. Honor the project's selected generation mode: in prompt-only mode, derive a fresh prompt from project facts and the page purpose, omit reference-image inputs, and do not translate a reference's layout or sample imagery into the prompt. Use explicit verbal style preferences where authorized. Reference conditioning or editing requires that intended use; shortlist approval alone does not authorize uploading images. When conditioning is authorized, send actual image bytes through a supported route; a filename in prose is not an uploaded reference. For continual-learning projects, also read [continual-learning-visuals.md](references/continual-learning-visuals.md); keep this project's precise algorithm and disclosure limits in its workspace. Explore distinct useful compositions when warranted, and report independent successful generations separately from crops and page placements.

Find references independently when the user cannot provide them; user-supplied images are optional. When the user requests reviewing references before production, preserve that preference across turns: research and prepare a visual shortlist first, then wait for their selection before any image-model call, including test concepts. Follow the approval-and-resume procedure in [visual-reference-library.md](references/visual-reference-library.md). Earlier generated images and agent recommendations do not constitute user approval.

1. **Understand the whole project and the user's intent before designing pages.** Read the actual sources and the current conversation. Establish the problem, end-to-end inputs/process/outputs, actual contribution/ownership, method, evidence and limits, then select the requested presentation scope. Identify audience, use context, duration, format and explicit content/layout preferences. Inventory reusable assets. Retain a compact `project_analysis` and `presentation_intent`; explain the intended story briefly to the user, and resolve consequential gaps using [visual-reasoning.md](references/visual-reasoning.md). Then write `design_synthesis`: the source-grounded story, audience priorities, necessary visual explanations, visual language, content density and delivery choice. Source correctness alone does not establish that the user wants this story or imagery. Derive these decisions afresh; do not inherit a previous project's template.
2. **Plan pages.** Write a version 2 `deck_plan.json` using [page-contract.md](references/page-contract.md). Separate page content, layout intent, theme, assets, and motion. Each content page must declare `visual_mode` (`generated`, `native_diagram`, `data_chart`, or `mixed`); mechanism pages must also declare `mechanism_visual` with visible input state, operation/decision, output state, relationship, and implementation layer. Each page needs a takeaway, the audience question it answers, a specific source focus, and source-grounded visual units: what operation, relationship, comparison, or evidence each unit communicates. Outline how adjacent pages advance the argument before designing isolated pages; a list of topics is not a story. Read [project-visuals.md](references/project-visuals.md) before planning content-page visuals; load its domain-specific reference only when relevant. A matching subject noun (kidney, network, robot) is not sufficient project relevance. Global project understanding is shared; page-specific work uses only relevant source excerpts. Do not mechanically assign the same outline to every topic.
3. **Choose a visual direction and density from the dialogue.** Analyze references for hierarchy, typography, composition, and image treatment; otherwise derive them from the project and stated use context. Read [layout-patterns.md](references/layout-patterns.md) for adaptive density and composition. A request for compact, information-rich pages changes the content budget and geometry, not merely font size. Coherent paired comparison pages can share a layout; unrelated pages should not all collapse into cards. Resolve the renderer using [renderer-routing.md](references/renderer-routing.md); native editability requirements take precedence over a preference for Slidev.
4. **Establish the sample design, then produce its assets.** For visual redesign, start with a short consecutive argument (often three pages), adapted to the story and requested page count, and include at least one complete mechanism page when the deck explains a method. For image-led visual exploration or requests for image-model aesthetics, prefer [design-first.md](references/design-first.md): generate a whole-page concept from the source-grounded page plan, inspect it, extract reusable parts, supplement only missing components, then reconstruct an editable sample. Otherwise sketch the reading order and image/native correspondence before producing assets directly. Use [image-pipeline.md](references/image-pipeline.md); the configured relay uses [proxy-backend.md](references/proxy-backend.md) and `scripts/prepare_assets.py`. New/revised asset plans declare `contract: "asset-contract-v2"`. Before any image request, run `python <skill-dir>/scripts/check_asset_plan.py --plan <absolute-asset-plan.json> --require-contract-v2`, then use `prepare_assets.py --plan <absolute-asset-plan.json> --require-contract-v2` for the configured relay; a failed contract blocks generation. For exploration declare distinct candidate entries and inspect the completed set before selection; a targeted single asset remains valid. Calibrate the assembled sample before expanding the batch; use two request workers by default and at most four when the relay permits. Keep exact data and topology in native/code elements. A generated concept retains `final_role: design_reference` and requires native reconstruction; it cannot be the final PPTX page or its rendered preview.
5. **Render representative pages.** Compose real pages using the actual assets. Inspect both presentation quality and project meaning: could this visual be moved to an unrelated project merely by replacing the title? If so, keep it only as declared decoration or redesign the explanatory layer. Inspect focal point, readability, cropping, and fidelity to evidence. Record concrete semantic and visual observations separately, bound to the inspected versions using `scripts/review_state.py` as described in the page contract. Review source → brief and prompt → image separately: an image can follow a misleading prompt perfectly. Fix the shared design before expanding the deck. A sample-only request ends at the requested samples; a full-deck request continues through final delivery without an extra approval stop unless the user requested one. Do not claim the user approved a sample they have not reviewed.
6. **Expand and repair locally.** Reuse the established type and spacing rules, while adapting composition to page purpose. Generate remaining assets and pages. Consolidate defects into a targeted repair pass; preserve good pages and assets. Default to one repair pass followed by verification, then surface unresolved defects instead of looping indefinitely. If a repair changes shared styling, recheck affected pages.
7. **Implement motion when useful/requested.** Use [motion.md](references/motion.md). Record what actually works in the presentation and its static-export treatment. An animation described in notes is not an implemented effect. Preview click states as well as the final readable static state.
8. **Validate and export.** Follow [quality-gates.md](references/quality-gates.md) and [qa-checklist.md](references/qa-checklist.md). Set `delivery.review_tracking: "sha256-v1"` for new/revised plans. Render all final pages from the deliverable, inspect them, record fresh page/export reviews, run `scripts/check_asset_plan.py --plan <absolute-asset-plan.json> --require-contract-v2` when a generated-asset plan exists, then run `scripts/check_deck.py --plan <absolute-deck-plan.json> --require-fresh-reviews`. Native mechanism pages declare actual nonzero `native_objects.diagram_shapes`, charts or tables; title text boxes cannot establish reconstruction. The checker compares actual object counts and embedded design-reference image hashes. It cannot judge beauty or independently verify human/agent review claims. Follow [export-runbook.md](references/export-runbook.md), use the actual export subcommand, and inspect the delivered file after export.

## Visual reasoning and clarification

When feedback identifies sparse content, disconnected imagery or oversized scenes, apply the claim-to-explanation and component-production steps in [project-visuals.md](references/project-visuals.md). Map the title's promise to visible intermediate details, then choose whole scenes or independently placeable parts and native relationships. Validate a fully assembled explanatory sample before expanding; a cover, an asset gallery or more elaborate prompts cannot substitute for that sample. Preserve useful evidence pages while repairing missing explanation.

Apply [visual-reasoning.md](references/visual-reasoning.md) during analysis and prompt review; reuse its established decisions rather than rereading it automatically. Trace the relevant input/state, operation/decision, output and unchanged conditions to sources, then identify the details the audience must actually see. Clarify consequential gaps in facts, intended message, image meaning or content density with one to three targeted questions after reading available material. When the user says imagery is strange or irrelevant, diagnose the mismatch before producing more assets. Hold only affected decisions while continuing independent work; use existing answers and do not create repeated approval gates.

Before calling the image backend, review each explanatory brief for source grounding, visible mechanism details, an appropriate scale/view, and the split between generated illustration and exact native/data layers. Save concrete prompt-review notes alongside the asset plan. Inspect those details again in the actual composed page; a record field or a successful API call is not semantic validation. Dimensional imagery should expose meaningful structure or interaction; coarse voxels and generic subjects are not a default style, and more pixels or pictures cannot repair a shallow mechanism analysis.

## Accuracy and image roles

- Preserve source values, units, formulas, citations, and claim boundaries. Identify missing evidence rather than inventing it.
- Distinguish factual evidence, explanatory diagrams, conceptual imagery, and decoration. Exact labels are composed in native/code elements around images.
- Choose the representation that carries each page's argument: a formula, code excerpt, sourced comparison, table, chart, diagram or image composite can all be appropriate. An attractive standalone subject plus generic prose does not demonstrate project-specific explanation. Generated images are optional layers, not a quota; a clear formula or evidence page need not have a generated illustration. Covers/dividers may use decoration alone.
- Apply the current domain's factual constraints. Generated illustrations cannot substitute for measurements, validated outputs or numerical simulations. Load the relevant domain reference through [project-visuals.md](references/project-visuals.md) when needed.
- Derive prompts from the project and page purpose. Do not bake a blue-purple palette, glass cubes, dark technology mood, or a fixed metaphor into every project. Maintain continuity without changing medium arbitrarily on every page.
- An image-led page must have an actual asset visibly placed in the final page. Having a prompt or a file on disk is insufficient.
- For repeated samples or constrained replacements, verify an identity ledger against every visible position. Reject extra changes and foreign-paper sample leakage; reconstruct the exact layer natively when necessary. Record actual image dimensions and output-hash-bound review findings.

## Delivery and execution

Deliver the requested deck, its selected renderer's editable/reproducible sources, referenced assets, page plan, final previews, and a concise statement of unresolved issues. For a PPT/PPTX request, default to native editable text, labels, tables, and suitable charts/shapes; bitmap illustrations can remain images. Slidev source editability does not make a raster PPTX editable. Whole-slide PNG packaging is only a disclosed visual preview or an explicitly requested image deck, never a silent shortcut for final native delivery. Record output mode and inspect the actual PPTX objects as well as its rendered pages. Do not require Slidev source for a native PPTX task. Keep credentials outside the project and never echo private configuration contents.

Track the current stage and meaningful progress. During generation inspect `asset_plan.state.json`; after an error report the affected asset and next action rather than waiting silently. On timeout, remote completion is unknown: do not automatically resubmit potentially billable requests. Resume selected failed work explicitly with `--only`; keep successful assets. Establish a useful rendered sample before expanding the batch. Keep one writer for each deck plan/export; asset-request concurrency is not an instruction to launch multiple agents. Preview servers are background services; do not wait for them to exit as a completion signal. Only stop a server owned by the current run when no longer needed; do not terminate another chat's work. Rendering errors, file completeness, content accuracy, and visual quality are separate checks.

For the verified upstream mechanisms and deliberately omitted features, read [upstream-lessons.md](references/upstream-lessons.md) when maintaining this skill. Do not import another tool's whole workflow or claim an integration that has not been implemented.
