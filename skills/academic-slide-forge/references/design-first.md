# Whole-page visual exploration, then editable reconstruction

Use this route when the user wants image-model visual quality combined with an editable deck. It is the preferred route for visually ambitious redesigns, not a requirement to generate a mockup for every table, formula or data page. It operates through the existing agent workflow and image runner; decomposition and reconstruction remain agent work.

## Establish the content before the image

Complete the whole-project map and requested-scope analysis first, using the existing research checkpoint. Whole-project understanding means covering the problem, end-to-end mechanism, contribution, evidence and limits; it does not require reading every file line by line. Resolve consequential gaps with targeted questions, then derive each page's promise, explanatory steps and necessary on-page detail. Retain the user's density preference.

Choose representative content pages for visual exploration, including a method/explanation page rather than only a cover. Write a whole-page design prompt from their actual content: reading order, focal relationships, meaningful local detail, intended text/data areas, image treatment and aspect ratio. Explore depth, composition and materials without prescribing one style for all projects. Reserve realistically sized areas for the actual native text; blank space that cannot hold the required explanation is not a workable design.

## Generate and select a design reference

First honor an active user request to review references before production: complete the visual shortlist and record their selection using [visual-reference-library.md](visual-reference-library.md). Do not call the image model for internal exploration while that requested review is pending. Once the selected reference set and output scope are approved, continue without asking for the same approval again.

Generate a whole-page visual concept as an internal design reference using the existing asset runner. Ask for composition and illustrative appearance, not authoritative equations, charts or text. Use blank text/data regions or simple visual placeholders; lay out real text in a draft renderer if needed to judge density. Any generated letters, numbers or apparent measurements are untrusted and must not become factual content.

For a weak visual direction, use [visual-reference-library.md](visual-reference-library.md) to select inspected references. Consider two or three distinct compositions with explicit explanatory jobs, such as system overview, mechanism cutaway and temporal storyboard. Multiple crops of one image do not test multiple compositions. This is exploration proportional to the user's request, not a per-page generation quota.

Declare exploration in `asset-contract-v2`: each candidate has its own ID, output and prompt, a shared `candidate_group`, `candidate_count_required` of two or three, a distinct `composition_id`, and `user_review_required: true`. Complete and inspect the set, present the actual candidates, and record the user's selection before reconstructing the selected exploratory direction. Do not turn one returned image into several alleged candidates by cropping. A focused single replacement can use `exploration_mode: single` and count one. A request to use a previously selected candidate does not reopen its selection.

Inspect whether the image explains the planned relationship and can be reconstructed at the requested density. Reject attractive concepts that omit the mechanism or require an enormous decorative object. Retain the selected image, prompt and brief under a project path such as `design/P03-concept-v1.png`. Record selection as an agent decision unless the user actually approved it. Show the sample when helpful without adding an approval stop the user did not request.

## Recover useful parts before generating more

Describe the selected concept's useful geometry, relative sizes and label anchors in the page composition for editable reconstruction. Keep that assembly record separate from new generation prompts: prompt-only supplemental jobs start from project facts and explicit verbal preferences, without translating the selected image's layout or sample imagery into prose. Make a concise component list in the existing asset brief with a source and an action for each part:

- Reuse existing project assets or clean crops from the reference when their resolution and bounds are adequate. Record the parent image and crop bounds for reproducibility. Cropping extracts pixels, not layers or hidden surfaces.
- Rebuild text, equations, charts, exact topology, selection marks and connectors with native/data elements. Remove the mockup's corresponding content; do not leave inaccurate labels or relationships visible under new overlays.
- Generate only missing or inseparable illustrative parts. For prompt-only jobs use a fresh project-derived prompt; user-approved verbal style anchors may be shared. Only authorized reference-conditioned jobs may use the selected reference's visual properties as generation guidance. Keep independently needed objects separable for editing or motion. Use reference-conditioned generation or local editing only through an implemented, verified API path.

The adapter can upload PNG/JPEG/WebP references through multipart image edits; verify the selected relay actually accepts that route before claiming reference-conditioned success. Declare each reference's role and forbidden transfers, then record its byte hash in metadata. See [proxy-backend.md](proxy-backend.md). Prefer reusable base assets and native overlays for consistent states. If a clean crop is impossible, generate an isolated replacement or use an intentional framed panel; do not assume a flattened image has recoverable alpha layers. Inspect edge quality and compositing after any masking. Preserve useful visual groups when splitting them would damage coherence; exact information must remain separate.

## Reconstruct, compare, then expand

Build a real editable sample from the extracted and supplemental assets. Compare its actual PPTX render side by side with the selected concept at the same size: visual hierarchy, density, image scale, local details, alignment, color and material continuity. Check the source-grounded explanation separately. Preserve the qualities that motivated the concept while correcting its factual defects; do not mechanically trace incorrect pixels.

Do not deliver the concept as a full-slide background with duplicate native text on top. That neither reconstructs the content nor provides practical editability. A concept keeps `asset_role` and `final_role` as `design_reference`, with `native_reconstruction_required: true`. Recovered illustration regions are separate declared components with parent path/hash and crop bounds. Exact states, relationships, labels and values must be rebuilt in native/data objects. Final mechanism pages need actual diagram shapes, charts or tables; a native title alone does not count. An explicitly requested image deck uses a separately disclosed raster-preview delivery, not a claim of editable reconstruction.

Repair specific losses in reconstruction before expanding to other pages. Apply the established design to related pages; create additional concepts only when their different explanation genuinely needs exploration. Data pages use real data graphics within the chosen visual language. Keep the existing bounded repair policy and batch concurrency; avoid generating every page twice.

Retain the selected concept path, component origins/actions, and concrete comparison observations in existing page composition, asset briefs and review notes. Keep the companion `asset_plan` linked from the deck plan even when its concept is not placed. A whole concept may appear on an explicitly marked `sample`/`design_reference` review page at sample stage; it is blocked as a final page asset, including an identical-byte copy with a different name embedded in PPTX. Final `preview` paths always identify renders of the delivered PPTX, not generated concepts. The checker enforces declarations, object counts and matching image bytes; decomposition quality and visual similarity remain inspection work. Save the next concrete action in the existing checkpoint so recovery resumes reconstruction instead of repeating research or generation.
